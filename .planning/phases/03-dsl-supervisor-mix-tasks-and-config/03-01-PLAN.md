<objective>
Implement the `use Orkestra.Projector` DSL macro and `Orkestra.Projection.Supervisor` so developers can define projectors declaratively and supervise them under a one_for_one strategy.

Purpose: This is the developer-facing surface that wraps Phase 2's runtime GenServer. Without this, developers must manually construct config maps and wire child_spec -- the DSL eliminates that boilerplate.

Output: `lib/orkestra/projector.ex` (DSL macro), `lib/orkestra/projection/supervisor.ex` (Supervisor), plus unit tests for both.
</objective>

**Generate `__dispatch__/3`** (called by Postgres adapter as `handler.(projector_name, event, position)`):
- IMPORTANT: The Postgres adapter calls `handler.(projector_name, event, position)` where the first arg is projector_name. However, `__dispatch__/3` needs to route by event type. So the dispatch function signature must be `__dispatch__(projector_name, event, position)` where it extracts `event.type` (a string like "MyApp.OrderPlaced") internally and routes.
- Generate one clause per handler: for each `{event_module, handler_fn}` in handlers, generate a clause that matches on `inspect(event_module)` as the type string, passes `(event, Ecto.Multi.new())` to the user's handler fn, and wraps the returned Multi as `{:ok, returned_multi}`. The user's fn signature is `fn event, multi -> multi |> ... end` per D-01.
- BUT: multi-clause def matching on `event.type` cannot be done via def head matching because event.type is inside a struct, not a positional arg. Instead, generate a single `__dispatch__/3` function with a `case event.type do` block dispatching to the correct handler, with a catch-all returning `:skip`. The GenServer handles `:skip` by proceeding with an empty Multi (no read-model write, just checkpoint).
- Wait -- actually, looking at the RESEARCH Pattern 2, it generates multi-clause `def __dispatch__(type_string, event, position)` matching on the type_string. This means the adapter_opts handler wrapper needs to extract the type before calling dispatch. The cleaner approach per RESEARCH:

  Generate the handler wrapper in `child_spec/1`:
  ```
  adapter_opts: [handler: fn projector_name, event, position ->
    __MODULE__.__dispatch__(event.type, event, position)
  end]
  ```

  And generate multi-clause `__dispatch__/3` with type_string as first arg:
  ```
  def __dispatch__("MyApp.OrderPlaced", event, _position) do
    {:ok, handler_fn.(event, Ecto.Multi.new())}
  end
  def __dispatch__(_type, _event, _position), do: :skip
  ```

  BUT: anonymous functions in child_spec/1 are not cleanly serializable across nodes. Instead, define a private `__handle__/3` in the module:
  ```
  @doc false
  def __handle__(projector_name, event, position) do
    __dispatch__(event.type, event, position)
  end
  ```
  And wire adapter_opts as `[handler: &__MODULE__.__handle__/3]`.

  This way `__dispatch__/3` matches on type string (clean multi-clause), and `__handle__/3` is the adapter-facing handler that bridges the signature gap.

  HOWEVER: the Postgres adapter's `write/4` expects the handler to return `{:ok, Multi.t()} | {:error, term()}`. When `__dispatch__/3` returns `:skip`, the `__handle__/3` wrapper needs to translate `:skip` into `{:ok, Ecto.Multi.new()}` (an empty Multi that commits fine with just the checkpoint). So:
  ```
  def __handle__(projector_name, event, position) do
    case __dispatch__(event.type, event, position) do
      {:ok, multi} -> {:ok, multi}
      {:error, reason} -> {:error, reason}
      :skip -> {:ok, Ecto.Multi.new()}
    end
  end
  ```

  IMPORTANT: The `__handle__/3` function references `Ecto.Multi.new()`. This means the function body needs Ecto at runtime. Since the module itself doesn't have a `Code.ensure_loaded?` guard, this call would fail if Ecto isn't present. To handle this correctly: wrap the `:skip` branch in a runtime check, OR (simpler) just document that `use Orkestra.Projector` requires Ecto as a dependency (which is already an optional dep -- the consumer must opt in). Since the consumer is defining projectors, they must have Ecto. This is consistent with how the EventStore.EventStoreDB requires Spear.

  Actually, even simpler: the `__handle__/3` wrapper can just return `{:ok, Ecto.Multi.new()}` for `:skip`. If Ecto isn't loaded, the module using `Orkestra.Projector` wouldn't compile correctly anyway since the handler fns reference `Ecto.Multi`.

Per D-05, D-06, D-07, D-08:

```elixir
defmodule Orkestra.Projection.Supervisor do
  @moduledoc """
  Supervisor for Orkestra projectors.

  Starts all configured projectors under a `one_for_one` strategy, ensuring
  that one projector crashing or halting does not affect others.

  ## Usage

  Add to your application's supervision tree:

      children = [
        {Orkestra.Projection.Supervisor, projectors: [
          MyApp.OrderProjector,
          {MyApp.CustomerProjector, repo: MyApp.CustomerProjection.TestRepo}
        ]}
      ]

      Supervisor.start_link(children, strategy: :one_for_one)

  ## Options

  - `:projectors` (required) - list of projector modules or `{module, opts}` tuples.
    Bare modules use their compile-time defaults; tuple form allows runtime overrides
    (e.g., different repo for test vs prod).
  - `:name` - registered name for the supervisor (defaults to `Orkestra.Projection.Supervisor`).
  """

  use Supervisor

  @spec start_link(keyword()) :: Supervisor.on_start()
  def start_link(opts) do
    projectors = Keyword.fetch!(opts, :projectors)
    name = Keyword.get(opts, :name, __MODULE__)
    Supervisor.start_link(__MODULE__, projectors, name: name)
  end

  @impl true
  def init(projectors) do
    children =
      Enum.map(projectors, fn
        {module, override_opts} -> module.child_spec(override_opts)
        module -> module.child_spec([])
      end)

    Supervisor.init(children, strategy: :one_for_one)
  end
end
```

Key points:
- `use Supervisor` (standard OTP)
- `start_link/1` accepts keyword opts with required `:projectors` key
- `init/1` maps each projector to its child_spec, handling both bare module and `{module, opts}` tuple forms per D-07
- Strategy is `:one_for_one` per D-06
- Name defaults to `__MODULE__` but is configurable via `:name` opt
- Minimal API per D-08: just `start_link/1` and `child_spec/1` (the latter auto-generated by `use Supervisor`)

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Compile-time macro expansion | Untrusted user opts flow into module attribute storage and code generation |
| child_spec config construction | User-provided repo/event_store modules are stored as atoms and passed to GenServer |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | T (Tampering) | projector.ex __using__ | accept | Macro opts are compile-time constants from the developer's own source code; no runtime user input |
| T-03-02 | E (Elevation) | projector.ex child_spec | accept | child_spec returns a supervisor spec -- only callable by the app's own supervision tree, not external input |
| T-03-03 | D (Denial of Service) | supervisor.ex | mitigate | one_for_one strategy with default OTP restart intensity prevents restart storms; halted projectors stay alive idle (Phase 2 design) |
</threat_model>
