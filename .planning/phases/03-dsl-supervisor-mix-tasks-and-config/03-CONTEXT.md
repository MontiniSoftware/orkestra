# Phase 3: DSL, Supervisor, Mix Tasks, and Config - Context

**Gathered:** 2026-06-24
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 3 delivers the **developer-facing surface** of the projection subsystem: the
`use Orkestra.Projector` DSL macro, the `Orkestra.Projection.Supervisor`, mix tasks
for per-projection migration management (migrate/rollback/drop/rebuild), and config
cleanup. Building on Phase 2's runtime GenServer and Ecto adapter, this phase makes
the subsystem usable by consuming applications — a developer defines a projector
module, adds it to a supervisor, runs migrations, and can trigger a full rebuild.

Out of scope (later phases): telemetry spans/metrics (Phase 4); MCP generators and
Queries module (Phase 5).

**Note on CFG-01 and CFG-03:** The `:ultimus` → `:orkestra` config key bug was
already fixed during Phase 1 code review (commit `1de9868`). Optional Ecto/Postgrex
deps are already declared in `mix.exs`. This phase focuses on CFG-02 (per-projection
Repo config story) and the remaining PROJ/MIG/RBLD requirements.

</domain>

<decisions>
## Implementation Decisions

### DSL Macro Design
- **D-01:** Event→handler mappings declared via `project EventType, fn event, multi -> ... end` macro — multiple declarations per module, each for a different event type. Unmatched events are silently ignored (the GenServer only routes events that have a registered handler).
- **D-02:** Projector config via compile-time `use` options: `use Orkestra.Projector, repo: MyRepo, event_store: MyStore, max_retries: 5, backoff_base_ms: 500, backoff_cap_ms: 30_000`. Mirrors the CommandHandler/EventHandler `use Module, opts` pattern.
- **D-03:** `projector_name` auto-derived from `inspect(__MODULE__)` with override via `name: "custom"` option — consistent with how CommandHandler derives topic names.
- **D-04:** The macro generates `child_spec/1` returning a spec for `Orkestra.Projector.GenServer.start_link/1` with the configured options — projectors are directly supervisable like CommandHandler/EventHandler.

### Supervisor & Registration
- **D-05:** Projectors passed as an explicit list to `Orkestra.Projection.Supervisor.start_link(projectors: [MyProjector1, MyProjector2])` — standard OTP conventions, no auto-discovery magic.
- **D-06:** `one_for_one` restart strategy — one projector crashing or halting does not affect others (success criterion 2).
- **D-07:** Supervisor accepts tuple form `{MyProjector, override_opts}` alongside bare module — lets the app override compile-time defaults per environment (e.g., different repo in test vs prod).
- **D-08:** Minimal supervisor API: just `start_link/1` and `child_spec/1`. Status/introspection deferred to Phase 4 telemetry and Phase 5 MCP.

### Mix Tasks & Rebuild
- **D-09:** Mix tasks discover the Repo via `__projection_config__/0` generated by the DSL macro — returns repo module, projector name, and migrations path. Tasks call this directly on the projector module.
- **D-10:** Per-projection migrations live in `priv/projections/<name>/migrations/` — fully isolated from app migrations and from each other. The `migration_source` table is `"projection_<name>_migrations"` (Ecto's `migration_source` option).
- **D-11:** `mix orkestra.projection.rebuild <name>` stops the projector GenServer → rolls back all projection migrations → re-migrates → resets checkpoint to -1 → restarts the projector (which catches up from position 0 via the existing subscription push model).
- **D-12:** Live transition after rebuild is natural: after the GenServer catches up from position 0 via the existing subscription push model, it's automatically live — no special transition needed (consistent with Phase 2 "no hard catch-up/live state machine" decision).

### Claude's Discretion
- Internal macro implementation details (`@before_compile`, module attribute accumulation for `project` declarations).
- Exact `__projection_config__/0` return shape (map vs keyword list).
- Mix task argument parsing and error message formatting.
- Whether rebuild should require a `--confirm` flag for safety.
- Test helper/fixture structure for DSL and supervisor tests.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- **`Orkestra.Projector.GenServer`** (`lib/orkestra/projector/gen_server.ex`) — the runtime being wrapped by the DSL; takes a config map with `repo`, `projector_name`, `storage_adapter`, `event_store`, `lifecycle_config`, `adapter_opts`.
- **`Orkestra.Projection.Storage.Postgres`** (`lib/orkestra/projection/storage/postgres.ex`) — the default storage adapter; the DSL can default to this.
- **`Orkestra.Projection.Migration`** (`lib/orkestra/projection/migration.ex`) — `up/0`/`down/0` for shared checkpoint/dead_letter tables; separate from per-projection read-model migrations.
- **`Orkestra.EventHandler`** (`lib/orkestra/event_handler.ex`) — reference macro pattern: `use Module, opts`, `@before_compile`, `defmacro __using__`, auto-generates GenServer + subscription wiring.
- **`Orkestra.Command`** (`lib/orkestra/command.ex`) — reference DSL macro: `Module.register_attribute`, accumulate macro calls, `@before_compile` to generate struct + builders.

### Established Patterns
- `use Module, opts` + `@before_compile` for DSL macros (Command, Event, CommandHandler, EventHandler).
- `child_spec/1` for supervisor integration (standard OTP pattern).
- Optional deps guarded with `Code.ensure_loaded?` (Ecto modules already follow this from Phase 1/2).
- Application config via `Application.get_env(:orkestra, Module, [])`.
- Mix tasks under `lib/mix/tasks/` namespace following `mix orkestra.*` convention.

### Integration Points
- DSL generates config map → `Projector.GenServer.start_link/1`.
- Supervisor starts projectors via `child_spec/1`.
- Mix tasks call `__projection_config__/0` on projector modules to discover Repo and migration paths.
- Per-projection migrations use Ecto's `migration_source` option for isolated migration tracking.

</code_context>

<specifics>
## Specific Ideas

- The `project` macro should accumulate event→handler pairs at compile time (like `param`/`field` macros) and the `@before_compile` callback should generate the routing dispatch used by `Storage.Postgres.write/4`'s `handler` option.
- CFG-01 (`:ultimus` fix) and CFG-03 (optional deps) are already done — Phase 3 only needs to establish the per-projection Repo config pattern (CFG-02) and document it in `@moduledoc`.
- The rebuild mix task should be the most complex task; migrate/rollback/drop are straightforward wrappers around `Ecto.Migrator` with the per-projection `migration_source`.

</specifics>
