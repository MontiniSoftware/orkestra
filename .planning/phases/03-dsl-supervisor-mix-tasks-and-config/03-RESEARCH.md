## User Constraints (from CONTEXT.md)

### Locked Decisions

**DSL Macro Design**
- D-01: Event-to-handler mappings declared via `project EventType, fn event, multi -> ... end` macro — multiple declarations per module, each for a different event type. Unmatched events are silently ignored.
- D-02: Projector config via compile-time `use` options: `use Orkestra.Projector, repo: MyRepo, event_store: MyStore, max_retries: 5, backoff_base_ms: 500, backoff_cap_ms: 30_000`. Mirrors CommandHandler/EventHandler `use Module, opts` pattern.
- D-03: `projector_name` auto-derived from `inspect(__MODULE__)` with override via `name: "custom"` option — consistent with how CommandHandler derives topic names.
- D-04: The macro generates `child_spec/1` returning a spec for `Orkestra.Projector.GenServer.start_link/1` with the configured options — projectors are directly supervisable like CommandHandler/EventHandler.

**Supervisor & Registration**
- D-05: Projectors passed as an explicit list to `Orkestra.Projection.Supervisor.start_link(projectors: [MyProjector1, MyProjector2])` — standard OTP conventions, no auto-discovery magic.
- D-06: `one_for_one` restart strategy — one projector crashing or halting does not affect others.
- D-07: Supervisor accepts tuple form `{MyProjector, override_opts}` alongside bare module — lets the app override compile-time defaults per environment.
- D-08: Minimal supervisor API: just `start_link/1` and `child_spec/1`. Status/introspection deferred to Phase 4 telemetry and Phase 5 MCP.

**Mix Tasks & Rebuild**
- D-09: Mix tasks discover the Repo via `__projection_config__/0` generated by the DSL macro — returns repo module, projector name, and migrations path. Tasks call this directly on the projector module.
- D-10: Per-projection migrations live in `priv/projections/<name>/migrations/` — fully isolated from app migrations and from each other. The `migration_source` table is `"projection_<name>_migrations"` (Ecto's `migration_source` option).
- D-11: `mix orkestra.projection.rebuild <name>` stops the projector GenServer → rolls back all projection migrations → re-migrates → resets checkpoint to -1 → restarts the projector (which catches up from position 0 via the existing subscription push model).
- D-12: Live transition after rebuild is natural: after the GenServer catches up from position 0 via the existing subscription push model, it's automatically live — no special transition needed.

## Summary

Phase 3 delivers the developer-facing surface of the projection subsystem. The three main deliverables are: (1) the `use Orkestra.Projector` DSL macro that wraps the Phase 2 `Projector.GenServer` and makes it supervisable with zero boilerplate; (2) `Orkestra.Projection.Supervisor`, a standard OTP `one_for_one` supervisor that accepts a list of projector modules and starts them as isolated children; and (3) four Mix tasks (`migrate`, `rollback`, `drop`, `rebuild`) that call `Ecto.Migrator` with per-projection paths and `migration_source` values derived from `__projection_config__/0` generated by the DSL.

The DSL macro follows the exact same pattern as the existing `Orkestra.Command` and `Orkestra.EventHandler` macros: `defmacro __using__(opts)` sets module attributes and imports the `project` macro; `@before_compile` accumulates the event-handler pairs and generates the dispatch function. The key new wrinkle is that `project` accumulates `{EventType, handler_fn}` pairs into a module attribute, and `@before_compile` generates a `__dispatch__/2` function that pattern-matches on event type and calls the appropriate handler.

The Mix tasks are the most structurally novel part of this phase. Each task calls `__projection_config__/0` on the named projector module to get `{repo, projector_name, migrations_path}`, then delegates to `Ecto.Migrator.run/4`. The rebuild task is the most complex: it must stop the GenServer, rollback all migrations, re-migrate, reset the checkpoint row, and restart the GenServer. Since GenServer restart is supervised, "restart" means stopping the child and letting the supervisor restart it automatically with the existing `one_for_one` strategy.

**Note on CFG-01 and CFG-03:** Both are already done. Confirmed by reading `lib/` (no `:ultimus` references) and `mix.exs` (ecto/ecto_sql/postgrex already optional deps). Phase 3 only implements CFG-02 (the per-projection config story via `__projection_config__/0` and moduledoc).

**Primary recommendation:** Build in three focused modules: `Orkestra.Projector` (DSL macro), `Orkestra.Projection.Supervisor`, and four Mix task files under `lib/mix/tasks/`. The macro generates `child_spec/1`, `__projection_config__/0`, and `__dispatch__/2` — the only three functions the outside world needs from a projector module.

### Pattern 1: DSL Macro with `@before_compile`

**What:** `defmacro __using__(opts)` registers a module attribute with `accumulate: true`, imports the `project` macro, and registers `@before_compile`. The `project` macro appends `{EventType, handler_fn}` to the attribute. `__before_compile__` generates `__dispatch__/2`, `__projection_config__/0`, and `child_spec/1`.

**When to use:** Any time compile-time accumulation of declarations needs to produce generated functions.

**Example** — directly analogous to `Orkestra.Command` pattern:
```elixir
# Source: lib/orkestra/command.ex (verified in codebase)
defmacro __using__(_opts) do
  quote do
    @behaviour Orkestra.Command
    Module.register_attribute(__MODULE__, :param_defs, accumulate: true)
    import Orkestra.Command, only: [param: 2, param: 3]
    @before_compile Orkestra.Command
  end
end

defmacro param(name, type, opts \\ []) do
  quote do
    @param_defs {unquote(name), unquote(type), unquote(opts)}
  end
end

defmacro __before_compile__(env) do
  param_defs = Module.get_attribute(env.module, :param_defs) |> Enum.reverse()
  # ... generates defstruct and new/2
end
```

For `Orkestra.Projector`, the adaptation:
```elixir
# Planned for lib/orkestra/projector.ex
defmacro __using__(opts) do
  repo           = Keyword.fetch!(opts, :repo)
  event_store    = Keyword.get(opts, :event_store, Orkestra.EventStore)
  projector_name = Keyword.get(opts, :name)  # nil = auto-derive in @before_compile
  lifecycle_cfg  = %{
    max_retries:    Keyword.get(opts, :max_retries, 5),
    backoff_base_ms: Keyword.get(opts, :backoff_base_ms, 500),
    backoff_cap_ms:  Keyword.get(opts, :backoff_cap_ms, 30_000)
  }

  quote do
    Module.register_attribute(__MODULE__, :projection_handlers, accumulate: true)
    Module.put_attribute(__MODULE__, :_projector_repo,          unquote(repo))
    Module.put_attribute(__MODULE__, :_projector_event_store,   unquote(event_store))
    Module.put_attribute(__MODULE__, :_projector_name_override, unquote(projector_name))
    Module.put_attribute(__MODULE__, :_projector_lifecycle,     unquote(Macro.escape(lifecycle_cfg)))

    import Orkestra.Projector, only: [project: 2]
    @before_compile Orkestra.Projector
  end
end

defmacro project(event_module, handler_fn) do
  quote do
    @projection_handlers {unquote(event_module), unquote(handler_fn)}
  end
end
```

### Pattern 2: `@before_compile` Generating `__dispatch__/2`

**What:** `__before_compile__` reads accumulated `@projection_handlers`, reverses the list (accumulate: true reverses declaration order), and generates a multi-clause `__dispatch__/2` function that matches on event type string, plus a catch-all that returns `:skip`.

**When to use:** When DSL declarations need to produce a runtime dispatch function.

```elixir
# Planned for lib/orkestra/projector.ex (before_compile callback)
defmacro __before_compile__(env) do
  handlers  = Module.get_attribute(env.module, :projection_handlers) |> Enum.reverse()
  repo      = Module.get_attribute(env.module, :_projector_repo)
  event_store = Module.get_attribute(env.module, :_projector_event_store)
  lifecycle = Module.get_attribute(env.module, :_projector_lifecycle)

  # projector_name: override or auto-derive
  name_override = Module.get_attribute(env.module, :_projector_name_override)
  # inspect(env.module) produces "MyApp.OrderProjector" — consistent with CommandHandler
  projector_name = name_override || inspect(env.module)

  # Derive migrations path from projector_name: "priv/projections/my_app_order_projector/migrations"
  # Note: path is a filesystem path; see Pitfall 3 for naming conventions
  slug = projector_name |> String.downcase() |> String.replace(".", "_")
  migrations_path = Path.join(["priv", "projections", slug, "migrations"])

  # Generate dispatch clauses
  dispatch_clauses =
    Enum.map(handlers, fn {event_module, handler_fn} ->
      type_string = inspect(event_module)
      quote do
        def __dispatch__(unquote(type_string), event, position) do
          unquote(handler_fn).(event, position)
        end
      end
    end)

  quote do
    unquote_splicing(dispatch_clauses)

    def __dispatch__(_type, _event, _position), do: :skip

    @doc false
    def __projection_config__ do
      {unquote(repo), unquote(projector_name), unquote(migrations_path)}
    end

    @doc false
    def child_spec(opts \\ []) do
      config = %{
        repo:            unquote(repo),
        projector_name:  unquote(projector_name),
        storage_adapter: Orkestra.Projection.Storage.Postgres,
        event_store:     unquote(event_store),
        lifecycle_config: unquote(Macro.escape(lifecycle)),
        adapter_opts:    [handler: &__MODULE__.__dispatch__/3]
      }
      config = Map.merge(config, Map.new(opts))
      %{
        id:    __MODULE__,
        start: {Orkestra.Projector.GenServer, :start_link, [config]}
      }
    end
  end
end
```

### Pattern 3: OTP Supervisor Wrapping a List of Projectors

**What:** `Orkestra.Projection.Supervisor` is a plain `Supervisor` module. `start_link/1` accepts `projectors:` list, maps entries to child specs (handling both bare module and `{module, opts}` tuple forms per D-07), and calls `Supervisor.start_link/2`.

**When to use:** When you need a named group of supervised workers with `one_for_one` isolation.

```elixir
# Planned for lib/orkestra/projection/supervisor.ex
defmodule Orkestra.Projection.Supervisor do
  use Supervisor

  def start_link(opts) do
    projectors = Keyword.fetch!(opts, :projectors)
    Supervisor.start_link(__MODULE__, projectors, name: __MODULE__)
  end

  @impl true
  def init(projectors) do
    children =
      Enum.map(projectors, fn
        {module, override_opts} -> module.child_spec(override_opts)
        module                  -> module.child_spec([])
      end)

    Supervisor.init(children, strategy: :one_for_one)
  end
end
```

### Pattern 4: Mix Task Calling `Ecto.Migrator` with Per-Projection Isolation

**What:** Each Mix task calls `__projection_config__/0` on the named projector module, starts the Repo if needed, and calls `Ecto.Migrator.run/4` with the per-projection `migration_source` applied via `Repo.put_dynamic_repo/1` or by configuring the Repo before start.

**Key insight on `migration_source`:** `migration_source` is a Repo config option, set per Repo in Application config or via `Ecto.Migrator.run/4` opts (as of ecto_sql 3.x, passing `migration_source:` is possible in opts). The per-projection Repo is configured in the consumer app's config file, including `migration_source: "projection_<slug>_migrations"`. The Mix task does NOT need to set `migration_source` dynamically — it reads the Repo's own config. [VERIFIED: Phase 2 `test_helper.exs` line 18: `migration_source: "orkestra_test_projection_schema_migrations"` is set per Repo in Application config]

```elixir
# Planned for lib/mix/tasks/orkestra.projection.migrate.ex
defmodule Mix.Tasks.Orkestra.Projection.Migrate do
  @shortdoc "Run migrations for a single Orkestra projection"
  @moduledoc """
  Runs all pending migrations for the named projection.

  Usage:
      mix orkestra.projection.migrate MyApp.OrderProjector
  """

  use Mix.Task

  @impl Mix.Task
  def run([projector_module_str | _rest]) do
    projector_module = String.to_existing_atom("Elixir.#{projector_module_str}")
    {repo, _name, migrations_path} = projector_module.__projection_config__()

    {:ok, _, _} =
      Ecto.Migrator.with_repo(repo, fn repo ->
        Ecto.Migrator.run(repo, migrations_path, :up, all: true)
      end)
  end

  def run([]) do
    Mix.raise("mix orkestra.projection.migrate requires a projector module name")
  end
end
```

### Pattern 5: Rebuild Task — Stop, Rollback, Re-migrate, Reset, Restart

**What:** `mix orkestra.projection.rebuild` executes a five-step sequence. The key challenge is stopping and restarting the GenServer through the supervisor. Since the supervisor is named `Orkestra.Projection.Supervisor`, we can use `Supervisor.terminate_child/2` and `Supervisor.restart_child/2` (or `Supervisor.delete_child/2` + re-add, but terminate/restart is cleaner for `one_for_one`).

**When to use:** Operator-triggered full replay of an event stream.

```elixir
# Planned for lib/mix/tasks/orkestra.projection.rebuild.ex
defmodule Mix.Tasks.Orkestra.Projection.Rebuild do
  @shortdoc "Rebuild an Orkestra projection from scratch"
  use Mix.Task

  @impl Mix.Task
  def run([projector_module_str | _rest]) do
    projector_module = String.to_existing_atom("Elixir.#{projector_module_str}")
    {repo, projector_name, migrations_path} = projector_module.__projection_config__()

    # Step 1: Stop the projector GenServer
    :ok = Supervisor.terminate_child(Orkestra.Projection.Supervisor, projector_module)

    # Step 2: Rollback all migrations
    {:ok, _, _} =
      Ecto.Migrator.with_repo(repo, fn repo ->
        Ecto.Migrator.run(repo, migrations_path, :down, all: true)
      end)

    # Step 3: Re-migrate
    {:ok, _, _} =
      Ecto.Migrator.with_repo(repo, fn repo ->
        Ecto.Migrator.run(repo, migrations_path, :up, all: true)
      end)

    # Step 4: Reset checkpoint to position -1
    alias Orkestra.Projection.Checkpoint
    repo.delete_all(Ecto.Query.from(c in Checkpoint, where: c.projector_name == ^projector_name))

    # Step 5: Restart — supervisor will call child_spec again, GenServer subscribes from -1
    {:ok, _pid} = Supervisor.restart_child(Orkestra.Projection.Supervisor, projector_module)
  end
end
```

**Important:** The rebuild task only works when the projector is running under `Orkestra.Projection.Supervisor` by name. If the projector is managed by the consumer's own supervisor, the task needs a different approach — see Pitfall 4.

### Anti-Patterns to Avoid

- **Calling `repo.start_link/1` inside a Mix task:** Use `Ecto.Migrator.with_repo/3` instead — it handles start/stop lifecycle and works in releases where Mix is unavailable. [CITED: https://ecto-sql.hexdocs.pm/Ecto.Migrator.html]
- **Setting `migration_source` dynamically in the task:** Set it in the consumer's Repo config (`Application.put_env` before start, or in `config.exs`). Dynamic override is fragile and bypasses the Repo's isolation contract.
- **Using `:erlang.binary_to_term` for event_type matching in dispatch:** Always match on the event type string (`event.type`), not on the atom module — the GenServer delivers bare maps with `type` as a string. [VERIFIED: `Projector.GenServer` `handle_info/2` uses `%{global_position: _} = event` — `event.type` is a string per `Orkestra.Event` struct definition]
- **Accumulating handler functions with closures that capture large data at compile time:** Handler functions should be anonymous fns that reference other functions, not closures over large data structures. Keep them as function references.
- **Registering the projector GenServer under its module name in `child_spec/1`:** The Phase 2 `Projector.GenServer.start_link/1` does NOT register a name by default. Registering by module name would prevent multiple projector instances (e.g., test vs prod). Name registration should be explicit and optional.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Per-projection migration isolation | Custom migration tracking table | `Ecto.Migrator.run/4` with `migration_source` Repo config | Ecto handles all migration locking, idempotency, versioning |
| Projector restart after rebuild | Custom process restart logic | `Supervisor.terminate_child/2` + `Supervisor.restart_child/2` | OTP Supervisor already owns the child lifecycle |
| Migration path detection | Custom `priv/` path resolution | Standard `priv/projections/<slug>/migrations/` convention | Predictable; same convention as Ecto's own `priv/repo/migrations` |
| Module name → task name resolution | Custom string manipulation | `Mix.Task` naming convention (module suffix → task name) | Elixir convention: `Mix.Tasks.Orkestra.Projection.Migrate` → `mix orkestra.projection.migrate` |
| Starting Repo before Ecto.Migrator | Manual `Repo.start_link` in Mix task | `Ecto.Migrator.with_repo/3` | Handles app startup, pool sizing for migrations, and cleanup |

**Key insight:** `Ecto.Migrator` already provides exactly the programmatic API needed for per-projection isolated migrations. All the complexity of version tracking, locking, and rollback is handled by passing a `[{version, Module}]` tuple list or a directory path. The only project-specific logic is deriving the correct `migrations_path` and `migration_source` from `__projection_config__/0`.

## Common Pitfalls

### Pitfall 1: `String.to_existing_atom` Fails if Module Not Loaded
**What goes wrong:** Mix tasks receive projector module name as a string argument. `String.to_existing_atom("Elixir.MyApp.OrderProjector")` raises `ArgumentError` if the module has never been loaded.
**Why it happens:** Atoms only exist in the atom table after the module is compiled and loaded.
**How to avoid:** Call `Mix.Task.run("compile")` (or `Mix.Task.run("app.start")`) before resolving the atom to ensure the project is compiled and modules are loaded. Alternatively use `Module.concat([string])` which is more forgiving.
**Warning signs:** `** (ArgumentError) argument error` when running the mix task in a clean shell.

### Pitfall 2: `@before_compile` Quoting Anonymous Functions
**What goes wrong:** Quoting `fn event, multi -> ... end` inside a macro and injecting it into generated code with `Macro.escape/1` is subtle. If the handler function references module attributes or imports from the calling module, they must be available in the right macro scope.
**Why it happens:** The `project EventType, fn -> ... end` call happens in the caller module context; the `@before_compile` callback runs in the macro module context. The fn AST is stored in the module attribute and re-injected during `@before_compile` — it must not rely on bindings that disappear between accumulation and generation.
**How to avoid:** Handler functions passed to `project` should only reference their arguments (`event`, `position`) and modules that are fully qualified. Avoid using module-level aliases (they resolve at definition time, not injection time). Document this constraint in `@moduledoc`.
**Warning signs:** `UndefinedFunctionError` or "undefined variable" compile errors in the generated `__dispatch__/2` clauses.

### Pitfall 3: `migration_source` Table Name Collisions
**What goes wrong:** Two projectors with similar names (e.g., `MyApp.OrderProjector` and `MyApp.Orders.Projector`) could produce the same `migration_source` string slug if the slug derivation is too aggressive.
**Why it happens:** Name normalization strips dots and lowercases — `MyApp.OrderProjector` → `"myapp_orderprojector"` vs `MyApp.Orders.Projector` → `"myapp_orders_projector"`. These differ, but a naive slug could collide.
**How to avoid:** Derive the slug consistently from the full module name, preserving all path segments: `"myapp.orderprojector"` → `"myapp_orderprojector"`. Use `String.replace(name, ".", "_") |> String.downcase()`. Document the derivation algorithm in the DSL module.
**Warning signs:** Migration history bleeding between projectors; one projector's rollback affecting another's migration table.

### Pitfall 4: Rebuild Task Assumes Named Supervisor
**What goes wrong:** `Supervisor.terminate_child(Orkestra.Projection.Supervisor, id)` fails with `:not_found` if the projector is managed by the consumer's own supervisor (not `Orkestra.Projection.Supervisor`).
**Why it happens:** The rebuild task assumes the projector runs under the library's named supervisor. But the consumer may use their own supervision tree.
**How to avoid:** Document clearly that `mix orkestra.projection.rebuild` requires the projector to be supervised under `Orkestra.Projection.Supervisor`. For other topologies, the developer must stop/start the projector manually. Alternatively, make the supervisor name configurable per task via a `--supervisor` flag (Claude's Discretion).
**Warning signs:** `** (EXIT) no process` or `:not_found` when running rebuild.

### Pitfall 5: `child_spec/1` ID Collision When Starting Multiple Instances
**What goes wrong:** If two projectors of the same module are started under the supervisor (e.g., for multi-tenant scenarios), their `child_spec` IDs both default to `__MODULE__`, causing `{:already_started, _}`.
**Why it happens:** `Supervisor.init/2` requires unique child IDs.
**How to avoid:** For v1, document that one module = one projector instance. The `id:` in `child_spec/1` is `__MODULE__`, which is unique per module. Tuple form `{Module, opts}` with an `:id` override would be needed for multi-instance (deferred).
**Warning signs:** `{:error, {:already_started, pid}}` when adding a projector that's already under the supervisor.

### Pitfall 6: Drop Task Leaves Orphaned Checkpoint Row
**What goes wrong:** `mix orkestra.projection.drop` that only rolls back migrations leaves the `projection_checkpoints` row intact. The next `mix orkestra.projection.migrate` + projector start would find the old checkpoint position and try to resume from it, but the read-model table no longer exists.
**Why it happens:** Checkpoint lives in the shared `projection_checkpoints` table (created by `Orkestra.Projection.Migration`), not in the per-projection migration path. Rolling back per-projection migrations doesn't touch the checkpoint.
**How to avoid:** The drop task must explicitly delete the checkpoint row: `repo.delete_all(from c in Checkpoint, where: c.projector_name == ^name)`. Document this explicitly. Also delete any dead_letter rows for the projector.
**Warning signs:** Projector crashes on startup with "no such table" after a drop+re-migrate cycle.

## Code Examples

### Mix.Task Definition
```elixir
# Source: https://mix.hexdocs.pm/Mix.Task.html [VERIFIED: WebFetch]
defmodule Mix.Tasks.Orkestra.Projection.Migrate do
  @shortdoc "Run migrations for a named Orkestra projection"
  @moduledoc """
  Runs all pending migrations for the named projection.

      mix orkestra.projection.migrate MyApp.OrderProjector
  """

  use Mix.Task

  @impl Mix.Task
  def run([projector_str]) do
    Mix.Task.run("app.config")  # ensure config is loaded
    module = Module.concat([projector_str])
    {repo, _name, path} = module.__projection_config__()

    {:ok, _, _} =
      Ecto.Migrator.with_repo(repo, fn repo ->
        Ecto.Migrator.run(repo, path, :up, all: true)
      end)
  end
end
```

## Open Questions (RESOLVED)

1. **`__dispatch__/3` vs `__dispatch__/2` arity** — RESOLVED
   - What we know: `Storage.Postgres.write/4` calls `handler.(projector_name, event, position)` — 3-arity
   - Resolution: The adapter `handler` is a 3-arity wrapper: `fn _name, event, position -> __MODULE__.__dispatch__(event.type, event, position) end`. The generated `__dispatch__/3` takes `(event_type_string, event, position)` and dispatches to the user's 2-arity fn. Unmatched types return `{:ok, Ecto.Multi.new()}` (skip). The `projector_name` arg is ignored in the dispatch (it's only used by the adapter for checkpoint writes).

2. **`project` handler function signature: `fn event, multi -> ...` vs `fn event, position -> ...`** — RESOLVED
   - Resolution: The user-facing `project` macro keeps the D-01 syntax: `project EventType, fn event, multi -> multi |> Ecto.Multi.insert(...) end`. The `multi` parameter is a pre-built empty `Ecto.Multi.new()` that the user chains operations onto and returns. The DSL wraps this internally: `user_fn.(event, Ecto.Multi.new())` returns the completed Multi, which the `__dispatch__/3` wrapper returns as `{:ok, result_multi}`. This preserves the CONTEXT.md D-01 syntax exactly while bridging to the Postgres adapter's expected `{:ok, Ecto.Multi.t()}` return type. The `position` is available via `event.global_position` if the user needs it.

### Known Threat Patterns for Stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Arbitrary module loading via `String.to_existing_atom` in Mix task | Tampering | `String.to_existing_atom` only loads atoms already in the VM (safe); module must be compiled first; Mix context limits exposure |
| SQL injection via projector name in `migration_source` | Tampering | Projector name is derived from module name (compile-time constant), not user runtime input; `migration_source` is a table name, not interpolated in queries by Ecto |
| Migration rollback deleting wrong projector's data | Elevation of Privilege | `migration_source` isolation ensures rollback only touches the named projector's migration table; Checkpoint delete is filtered by `projector_name` |

**V5 note:** The CLI argument `projector_str` is the only external input. Using `Module.concat([projector_str])` instead of `String.to_existing_atom` is safer for error messages. The consumer controls which modules are compiled — this is an operator-facing tool, reducing risk. [ASSUMED: Mix task security surface is low for a library development tool]
